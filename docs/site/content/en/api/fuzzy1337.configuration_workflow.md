# fuzzy1337.configuration_workflow

Experimental SCAN-only product SDK workflow for the five reviewed owned synthetic
Dockerfile/Kubernetes specimens. `ConfigurationScanSelection` requires explicit
synthetic profile, logical path, absolute source/runtime/worker/material selections
and selected-read consent. Native configuration and arbitrary file scanning remain
unavailable.

`RunSyntheticConfigurationScan` uses actual canonical prepare, grant, governed
execution and fresh acceptance interfaces, then preserves original source/stream/
receipt evidence. It validates the exact processed wire and source coordinates and
saves canonical configuration ASSETs/Findings with optimistic model revision checks.
Workspace evidence/object/job references precede a successful model-delta event.
Current scope owner, consent, selected material and original stage must still match.

`ConfigurationScanSummary` retains actual terminal job, committed model revision,
operation outcomes and explicit `not-assessed` completeness. Requested JSON/SARIF
export uses existing report owners to publish the exact saved snapshot, with a
separate `ConfigurationReportOutcome`. `ExportConfigurationReport` reports actual
publication and failure truth without changing original completed scan facts.
Model and workspace remain distinct stores; a subsequent workspace-save failure is
reported honestly with the actual saved model revision.

The exports in `__all__` are supported Experimental interfaces. Internal provider
helpers are not a separate grant, policy, evidence or model owner. No process flag,
environment overlay, worker registration, implicit path discovery or native
compatibility fallback is exposed. See [the workflow guide](https://github.com/Fuzzy-Technologies/1337/blob/develop/docs/CONFIGURATION_WORKFLOW.md).
